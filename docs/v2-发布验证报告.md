## 7.1 真实设备首次重启后插件未加载（已定位并修复）

**现象**：安装 v2 后首次重启 DSH，侧边栏没有「同步」按钮；8732 无监听；profile 的 `dsh.profile.bundles` 中插件条目消失。

**排查**：
- 安装后确认过 bundles 含插件；重启后被移除；
- DSH 启动日志出现 `DesktopHostFatalError: cannot create effect on inactive context`（dsh-desktop-host）；
- 对比旧插件：v1 的 `apply` 是**同步**函数，在同步阶段注册 `ctx.effect`；v2 的 `apply` 是 async，`await startServer(...)` 之后才调用 `ctx.effect`，此时上下文可能已失活。

**修复**：
- `plugin-v2/index.js` 改为同步注册 `ctx.effect`（只负责关闭服务），HTTP 服务在 effect 之外异步启动，返回的 Promise 仅用于测试/工具等待就绪；
- 集成测试/端到端测试的 effect fake 同步调整并通过（23/23、14/14）；
- 重新执行安装脚本，恢复 profile bundles 条目（新备份 `package.json.bak-20261120194924`）。

## 7.2 真实 DSH 加载失败的最终根因与修复（2026-11-23）

**排查工具**：DSH 官方 `plugin_manager` 的 `list_plugins` 显示：

```
include:cloud-sync-panel  moduleName: dsh-plugin-cloud-sync-panel
enabled: true  fiberPhase: "failed"
diagnostic: cannot get property "workspaceRegistry" without inject
```

**根因**：v2 的 `apply` 直接读取未声明 `inject` 的服务（`ctx.workspaceRegistry` / `ctx.directoryPicker`），Cordis 抛错导致插件 fiber 挂载失败；因此 8732 无服务、界面无按钮。此前观察到的 profile bundles 被回收是 DSH 启动异常后的恢复机制叠加结果。

**修复**：
- 入口改为 `ctx.get('workspaceRegistry')` / `ctx.get('directoryPicker')` 安全获取，失败降级 undefined；
- 保留同步注册 `ctx.effect`、`apply` 返回 void 的契约；
- 入口增加启动诊断日志 `%DSH_HOME%/cloud-sync/plugin-startup.log`。

**验证**（未重启 DSH，用官方重载）：
- `plugin_manager set_bundle` 禁用 → 启用，返回 `application: applied`；
- `list_plugins`：`include:cloud-sync-panel` → `fiberPhase: active`；
- `http://127.0.0.1:8732/api/health` → `{"ok":true,"service":"cloud-sync","version":"2.0.0-alpha.1"}`；
- `tools/v2/verify-runtime.mjs` → **9/9 通过**（P1/P2 + R1-R7）；
- 真实数据读取：仓库 1 个（主仓库）、项目树 5 个项目/10 个会话、注册表 valid。

**结论**：插件加载链路在真实 DSH 上已打通；剩余为界面点击验收。

## 7.3 外部缺陷报告修复：CORS 预检导致 Web 界面写操作全失败（2026-11-23）

来源：另一台设备（DSH 0.2.0-rc.2）的测试报告（页面 origin 与 8732 不同端口，跨源）。

**缺陷**：
- 服务端 OPTIONS 预检只返回 `Access-Control-Allow-Origin`，缺 `Access-Control-Allow-Headers`（content-type）与 `Access-Control-Allow-Methods`；
- 浏览器在预检阶段拒绝，所有 POST（添加/移除仓库、上传、下载）报 `Failed to fetch`，而 Node 集成测试无 CORS 强制，完全测不出；
- 附带缺陷：`removeRepo` 禁止移除最后一个仓库，导致死记录无法清理，且业务错误被报成 500。

**修复（v2.0.0-alpha.2）**：
- `lib/host/server.js`：统一 CORS 头；OPTIONS 预检返回 204 + `Allow-Headers: content-type` + `Allow-Methods: GET, POST, OPTIONS` + `Max-Age: 600`；
- `lib/host/routes.js`：/api/health 版本号改为动态读取 package.json；
- `lib/core/repo.js`：允许移除最后一个仓库（空注册表合法）；业务错误改用 `AppError`（HTTP 400）；
- 回归测试：集成新增 CORS 预检三项 + 移除最后仓库一项（27/27）。

**真实 DSH 热重载验证**（无需重启）：
- `plugin_manager set_bundle` 禁用→启用：`application: applied`；
- health：`{"service":"cloud-sync","version":"2.0.0-alpha.2"}`；
- 预检：`204; allow-headers=content-type; allow-methods=GET, POST, OPTIONS`；

## 7.5 下载目录与系统选择框（v2.0.0-alpha.5，2026-11-23）

## 7.7 会话迁移后旧副本未清理（v2.0.0-alpha.9，2026-11-23）

**现象**：把会话从旧工作区迁到新工作区后，同一会话在 `%DSH_HOME%\sessions` 下存在两份副本（旧 projectKey/新 projectKey），侧边栏分组混乱。

**根因**：
- `downloadSession` 会把会话写到 `sessions/<新 cwd 路径键>/<id>/`，但只**报告** `duplicates`，从未清理旧 projectKey 下的副本；

**修复（alpha.9）**：
- `downloadSession` 新增迁移语义（默认 `migrate:true`）：迁移成功后把其它 projectKey 下的同 ID 会话目录 **移动**到 `<DSH_HOME>/cloud-sync/session-trash/<ts>/<projectKey>/<id>`（不直接删除，可恢复）；
- 下载接口/前端新增「迁移会话（清理旧位置副本）」开关（默认勾选）；
- 上传会话时优先选择“会话头 cwd 与目标 cwd 一致”的副本，避免多副本时传错；
- 拆分 `session-download.js`，保持单文件规模约束；
- 回归：单元 18/18、集成 39/39（新增 Y2 旧副本已清理、Y3 移入 session-trash），门禁 8/8。

**存储职责说明**（本次审查结论）：
- 会话：`%DSH_HOME%\sessions\<cwd 路径键>\<4f1a话ID>\session.v4.jsonl.zstd`，路径键由会话 cwd 推导，DSH 侧边栏按 cwd 分组；

## 7.9 工作区下无会话（v2.0.0-alpha.13，2026-11-23）

**现象**：云端项目里有会话，同步提示正常，但工作区（云端项目行/DSH 侧边栏）显示无会话。

**两个独立根因**：
1. **视图归行**：`buildTree` 先统计全局 `localIds` 再跳过已存在的云端会话；当本地副本与云端会话 `cwd` 不同（例：Desktop vs workspaces 目录）时，云端项目行会被判为 0 个会话，无法从云端行下载。
2. **工作区登记**：官方 `workspaceRegistry.resolveByPath()` 是 **async**，代码漏了 `await`，它返回的 Promise 恒为真 → 跳过 `create()`，工作区从未真正登记；即使创建了，也没调用 `Workspace.attachSession()` 将会话挂到工作区账上。

**修复（alpha.12/alpha.13）**：
- `buildTree` 改为按会话自己的 `cwd` 归行；仅当该行已有同 ID 会话时才跳过（T1 回归）；
- 两处 `resolveByPath()` 补 `await`；
- 登记/下载后对 cwd 匹配的会话逐个 `attachSession(id)`，返回 `attached` 列表；
- 单测新增 `tests/unit/workspace_register.test.mjs`（覆盖 async resolveByPath 与 create 调用）。

**真实环境验证**：
- 云端项目行（cwd=Desktop）会话数从 0 → 2；
- 重新登记 `C:\Users\28726\Documents\deepseek-harness\workspaces\航天器课程作业`：返回 `attached=[0662b1c2, 7770e0f8]`，注册表 `sessionIds` 为 2，`/api/workspaces` 显示 sessions=2。

## 7.10 工作区可见但会话不显示：子会话（v2.0.0-alpha.16，2026-11-24）

**现象**：工作区已在侧边栏显示，但下面没有会话。

**诊断**（只读）：
- 注册表 `sessionIds` = 2，`/api/workspaces` 过滤后 sessions=2；
- DSH `sessionPersistence.list()` 返回的 13 个会话包含这 2 个，`sessionKnown(id)` 均为 true；
- 但这 2 个会话的 header 为：`origin: "subagent"`、`parentSession: "session-88e455b8-8a87-4f10-9a0b-6ffbe9e9a421"`、`delegationDepth: 1`。

**根因**：DSH 侧边栏按设计只列普通会话；官方会话列表语义为“ordinary forks, including historical logs with parentSession; **origin: subagent remains excluded**”。云端只上传了这两个子会话（父会话未上传），所以侧边栏看不到主对话。
