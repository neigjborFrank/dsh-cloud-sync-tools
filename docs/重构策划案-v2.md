# DSH 云端同步插件重构策划案（v2）

> 文档版本：v2.0-draft ｜ 日期：2026-11-20 ｜ 状态：待评审
> 适用仓库：`dsh-cloud-sync-tools`（工具/代码） + 用户私有数据仓库（如 `deepseek_cloud`）
> 本文档是多颗粒度设计：L0 一页纸 → L1 模块 → L2 数据 → L3 接口 → L4 流程 → L5 代码工程。

---

## L0 一页纸（先读这里）

**要做什么**：把当前"能跑但混乱"的云端同步插件，按清晰架构重写为 v2；保留并复用已有可用资产，保证旧数据可读、旧功能不丢。

**核心功能**（一句话一条）：
1. 在 DSH 内把「工作区 + 会话」按项目归档到用户自己的私有 Git 仓库；
2. 多仓库登记，逻辑上合并查看，上传时选择/记住目标仓库；
3. 上传时智能分析工作区包含关系，按最大工作区合并（子目录并入父项目、小项目并入大项目）；
4. 下载时选位置、镜像工作区、改写会话 cwd、自动登记为新工作区；
5. 「云端与同步」视图按 工作区 → 会话 层级显示同步状态；
6. 版本历史交给 Git/GitHub（插件自身不再维护备份/回滚）；
7. 一键安装 / 一键更新（Windows），新设备从公开工具仓库起步；
8. 安全兜底：不自动连接任何仓库、不破坏 DSH 的 workspace 注册表、不把工作区放安装目录。

**仓库数据布局（已定）**：存储区 `store/<最大工作区>/files|large/` + 指示区 `index/projects/<项目>/{meta,manifest,large,conflicts,sessions}`。

**当前主要问题**：单文件过大（index.js 909 行、client.js 753 行）、职责混杂、API 与视图逻辑纠缠、文档/测试/旧代码口径不一致、历史包袱（旧 `projects/<项目>/workspace/` 布局、已删除的备份/回滚机制仍散落引用）。

**重构方式**：不改用户可见的核心行为，重排代码边界；新代码按模块拆分，旧代码归档到 `legacy/v1/` 供对照与回滚。

**分 7 期**：M0 策划（本阶段）→ M1 骨架与数据层 → M2 会话/仓库层 → M3 Host API → M4 前端 → M5 安装/发布 → M6 清理验收。

## 1. 背景与问题诊断

### 1.1 当前资产规模

| 文件 | KB | 行数 | 问题 |
|---|---:|---:|---|
| `plugin/index.js` | 39.6 | 909 | HTTP 服务 + 路由 + 业务 + Git 操作 + 视图聚合全部混在一起 |
| `plugin/client.js` | 34.5 | 753 | 菜单、选择器、上传/下载向导、仓库管理、视图渲染都在一个文件 |
| `plugin/lib/projects.js` | 20.3 | 471 | 目录约定 + 包含关系分析 + 合并迁移 + 下载镜像混合 |
| `plugin/lib/archive.js` | 16.1 | 446 | 会话枚举/HTTP 会话上传下载/cwd 改写/pending 检查混合 |
| `plugin/lib/store.js` | 8.0 | 207 | 清单 + 镜像 + 合并 + 大文件（尚可，但可再拆） |
| `plugin/lib/registry.js` | 10.0 | 241 | DSH workspace.json 安全写入与自愈（较独立，可原样复用） |
| `plugin/lib/repos.js` | 7.9 | 204 | 多仓库 + 绑定（可复用，需加 schema 版本） |
| `tests/*` | 41 | 533 | 4 个集成测试，覆盖好但路径/API 口径随版本漂移 |
| `install/*` | 33 | 316 | 安装/更新脚本可用，但错误处理与幂等性一般 |
| `docs/*`、`logs/*` | 41 | 470 | 文档滞后于实现，日志是历史记录 |

### 1.2 具体混乱点

1. **God file**：`index.js`/`client.js` 职责过多，改动一处容易牵连全部；
2. **双布局残留**：代码里同时兼容 `projects/<项目>/workspace/`（v1）与 `store/ + index/`（v2）；
3. **已废弃逻辑残留**：备份/回滚虽已删除，但文档、报告、测试里仍有引用；
4. **API 冗余**：既有 v2 的 `/api/tree`、`/api/cloud-view`、`/api/repos`，也保留 v1 的 `/api/check`、`/api/upload`、`/api/download`（git 整仓同步遗留）；
5. **前端无组件化**：一个文件里手写字符串 HTML，状态（treeCache/bindings/currentProject）全局散落；
6. **测试与实现耦合**：测试直接读仓库内部路径，布局一改测试就失效（本轮已发生）；
7. **文档口径不一**：安装说明、README、日志报告描述不同时期的形态。

## 2. 目标与非目标

### 2.1 目标

- G1 功能等价：v1 已验收的行为在 v2 全部保留（含合并、冲突隔离、绑定、多仓库、LFS、cwd 改写、注册表安全）；
- G2 结构清晰：单文件 ≤ 300 行，模块边界单向依赖，路由/业务/视图/存储分层；
- G3 可测试：核心逻辑（清单、合并、迁移、镜像、cwd 改写、注册表）都有单元测试，集成测试不依赖内部路径；
- G4 可迁移：旧数据仓库无需人工改造即可读；安装/更新脚本可覆盖升级；
- G5 可维护：文档与代码同版本；旧代码归档可查；
- G6 安全不变：不自动登记仓库、不写坏 DSH 注册表、不往安装目录放数据。

### 2.2 非目标

- 不做账号级/云端服务端（继续用用户自己的 Git 私有仓库）；
- 不做自动创建 GitHub 仓库（需要 Token，已决定不做；用户自行整理仓库）；
- 不做插件自身版本备份/回滚 UI（历史交给 Git/GitHub）；
- 不做移动端/Web 独立端（仍在 DSH 宿主内）。

| R9 | 云端与同步视图：工作区 → 会话 层级、同步状态（一致/有改动/未上传/仅云端/已归档） |

| R11 | 注册表安全：写前备份、写后按 DSH 规则校验、失败回滚、启动自愈 |

## 6. L2 数据与仓库布局（数据结构定义）

### 6.1 云端仓库

```
<repo>/
├── store/                                  # 存储区（只放内容）
│   └── <最大工作区项目名>/
│       ├── files/<原始相对路径...>          # 工作区内容（保持层级，可人工浏览）
│       └── large/<原始相对路径...>          # 大文件内容（git-lfs）
└── index/                                  # 指示区（只放结构与映射）
    └── projects/<项目名>__<路径键>/
        ├── meta.json                       # 项目元数据（含 aliases）
        ├── manifest.json                   # 路径 → {hash,size}
        ├── large.json                      # 大文件清单
        ├── conflicts/<ts>/<路径>            # 合并冲突隔离
        └── sessions/<会话id>/
            ├── session.v4.jsonl.zstd
            ├── meta.json                   # 会话元数据
            └── workspace-ref.json          # 结构快照引用
```

### 6.2 Schema（带版本号，便于演进）

```jsonc
// meta.json
{
  "schema": 1,
  "name": "test__D-deepseek-workspace-test",
  "cwd": "D:\\deepseek\\workspace\\test",
  "projectKey": "--D-deepseek-workspace-test--",
  "title": "test",
  "aliases": [{ "cwd": "D:\\deepseek\\workspace\\test\\sub", "scope": "sub" }],
  "sessions": ["session-..."],
  "storeRoot": "test__D-deepseek-workspace-test",
  "createdAt": "...", "updatedAt": "..."
}

// manifest.json
{ "schema": 1, "createdAt": "...", "files": { "notes/2025/a.md": { "hash": "sha256", "size": 123 } }, "large": [], "tooLong": [] }

// sessions/<id>/meta.json
{ "schema": 1, "id": "session-...", "title": "...", "cwd": "...", "project": "test__...", "scope": "sub", "sessionFile": "session.v4.jsonl.zstd", "sessionBytes": 12345, "uploadedAt": "..." }

// sessions/<id>/workspace-ref.json
{ "schema": 1, "project": "test__...", "scope": "", "manifestHash": "sha256", "files": 15, "capturedAt": "..." }

// repos.json（本机 DSH_HOME/cloud-sync/repos.json）
{ "schema": 2, "repos": [{ "id": "repo-xxxx", "name": "主仓库", "url": "...", "path": "...", "branch": "main", "addedAt": "..." }], "bindings": { "<项目名>": "repo-xxxx" } }
```

### 6.3 合并数据规则（复用现有语义）

| 场景 | 处理 |
|---|---|
| cwd 相同 | 镜像更新该项目（删除已移除文件） |
| 新工作区是项目子目录 | 写入 `<scope>/路径`，记录 alias |
| 新工作区包含项目 | 旧项目迁入新项目（加前缀），删除旧项目，迁移 aliases/sessions |
| 同路径不同内容 | 保留云端旧版，新内容进 `conflicts/<ts>/`，返回冲突列表 |
| 大文件 >95MB | 内容进 `large/`（LFS），清单记录路径/大小/哈希/存储状态 |
| 路径 >220 字符 | 跳过并记录 `tooLong` |

### 6.4 旧布局兼容

- 读：`index/projects` 不存在时回退 `projects/`；项目内 `manifest.json` 不存在时回退 `workspace/manifest.json`；store 内容回退 `<项目>/files`。
- 写：一律写新布局；不自动迁移旧目录（M6 提供一次性迁移脚本，可选执行）。

## 7. L3 API 契约

统一前缀 `/api`，除 `/health`、`/token` 外均需 `?token=`；失败返回 `{ ok:false, error:"code", output:"中文说明" }`。

### 7.1 视图

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | `{ok:true, service, version}` |
| GET | `/api/tree` | `{ repos[], bindings, suggestedBase, projects[{name,title,cwd,cloudProject,sessions[]}] }` |
| GET | `/api/cloud-view` | `{ repo, repos[], totals{projects,sessions,pendingWorkspaces,pendingSessions,ignoredInstall}, projects[{name,title,cwd,repoIds,repoNames,boundRepo,workspace{status,changed,added,removed,...},sessions[{id,title,state}...]}] }` |
| GET | `/api/sessions` | 本机会话列表（含 cwd/title/archived） |
| GET | `/api/registry-status` | DSH workspace 注册表校验结果 |

### 7.2 仓库

| 方法 | 路径 | 请求 | 说明 |
|---|---|---|---|
| GET | `/api/repos` | — | `{repos[], bindings, defaultRepoId}` |
| POST | `/api/repos` | `{url?, path?, name?}` | 登记（邮箱 URL 克隆 / 本地路径），URL 唯一 |
| POST | `/api/repos/remove` | `{id}` | 取消登记（不删本地克隆），清理绑定 |

### 7.3 上传 / 下载

| 方法 | 路径 | 请求 | 说明 |
|---|---|---|---|
| POST | `/api/upload-project` | `{repoId, cwd, sessionIds[]}` | 分析→合并→上传→提交推送；返回 `{ok, output, projectName, scope, mergedInto?, migrated?, conflicts[]}` |
| POST | `/api/download-project` | `{repoId, name, targetDir, sessionIds[], withWorkspace}` | 镜像+会话+cwd 改写+登记；返回 `{ok, output, workspace{written,verified,failed,trashed,largeRestored}, pendingLarge[], registration}` |
| POST | `/api/pick-directory` | `{}` | 原生文件夹选择框；无原生能力时 `{available:false}` |

### 7.4 管理

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/registry-repair` | 修复 DSH 注册表重复登记 |
| GET/POST | `/api/config` | 建议下载位置、安装目录风险检测 |

> v1 遗留接口（`/api/check`、`/api/upload`、`/api/download`、`/api/diff`、`/api/upload-sessions`）在 v2 **删除**，不保留兼容层（客户端同版本升级）。

## 8. L4 关键流程

### 8.1 上传（含合并决策）

```
选择项目+会话+仓库
   │
   ▼
buildManifest(cwd) ──► analyzeUpload：与目标仓库所有项目比较 cwd 祖先/后代 + 清单包含
   │
   ├─ 同 cwd ─────────────► mirror 更新项目（冲突进 conflicts/）
   ├─ 当前是子目录 ───────► 写入父项目 <scope>/路径 + alias
   ├─ 当前包含旧项目 ─────► 旧项目迁移进新项目（前缀/alias/会话），删除旧项目
   └─ 无包含关系 ─────────► 新项目 + 新 store 树
   │
   ▼
写 store 文件 + index 清单 + 会话 + workspace-ref
   ▼
git add/commit/push（失败回滚提示，不破坏工作区）
```

### 8.2 下载

```
选择项目+会话 → 选目录（原生选择框/输入）→ 勾选“同时下载工作区”
   ▼
downloadProjectWorkspace：镜像、多余文件进 .csp-trash-<ts>、逐文件哈希校验、LFS 恢复
   ▼
downloadSession：cwd 改写 → 本机 sessions/<projectKey>/<id>/；projcache 更新
   ▼
workspaceRegistry.create(target,targetTitle)（不可用则回退注册表文件）
   ▼
结果：写入/校验/失败/回收/大文件待人工清单/登记结果
```

### 8.3 云端与同步视图

- 合并所有仓库的项目（按项目名），标仓库名与绑定仓库；
- 工作区状态：一致 / 有未上传改动（改/增/删）/ 云端未上传 / 本地缺失；
- 会话状态：一致 / 内容不同 / 未上传 / 仅云端 / 已归档；
- 本地 cwd 通过 aliases 归并到父项目行；安装目录内未上传工作区忽略并在汇总注明。

### 8.4 启动自检（每次 DSH 启动）

1. `registry.js` 校验并自愈 workspace.json（重复登记）；
2. 确保 `repos.json` 存在（**绝不自动登记仓库**）；
3. `git lfs install --local`（失败降级）；
4. 启动 HTTP 服务（仅回环）。

### 8.5 安装 / 更新

- 安装：定位克隆 → profile `package.json` 加 link + bundle → pnpm install → 仓库基础配置（longpaths/身份/分支）→ **不登记同步仓库**；
- 更新：`git pull --ff-only` → 若插件代码变化则 `pnpm install` → 提示重启；
- 回滚：`plugin/回滚.cmd` 恢复 profile 快照。

## 9. L5 代码工程规范

### 9.1 目录

```
plugin/
├── index.js                 # 唯一入口：apply(ctx, config) → 启动 server
├── client.js                # 客户端 bundle 入口（构建/加载）
├── lib/
│   ├── host/  server.js  routes/*.js
│   ├── core/  manifest.js mirror.js merge.js project.js session.js repo.js registry.js git.js lfs.js layout.js
│   └── shared/ constants.js errors.js logger.js
├── client/  entry.js api.js ui/*.js styles.css
├── cordis.patch.yml
└── package.json
```

### 9.2 约束

- 单文件 ≤ 350 行（`client.js` 因 DSH 脚本加载约束保持单文件，≤ 800 行）；单函数 ≤ 80 行；
- core 纯函数优先，I/O 集中在少数模块；所有写文件走 `fs-utils`（原子写、长路径）；
- 错误统一 `AppError{code,message,detail}`；日志分级 `log.info/warn/error`，写入 DSH 日志（不弹窗）；
- 无第三方运行时依赖（仅 Node 内置）；前端无框架（原生 DOM），样式集中 CSS；
- 所有对外中文文案集中在 `shared/messages.js`（便于统一与测试）；
- schema 带版本号，读时校验、写时声明；
- 禁止在 core 出现 HTTP 概念，禁止在 routes 拼存储路径（用 core API）。

### 9.3 测试分层

| 层 | 内容 | 位置 |
|---|---|---|
| 单元 | manifest/mirror/merge/project/session/registry 纯逻辑 + 临时目录 | `tests/unit/` |
| 集成 | 多仓库、上传/下载/合并/复杂文件、注册表自愈 | `tests/integration/` |
| 端到端 | 安装脚本 dry-run、插件加载、API smoke | `tests/e2e/` |

质量门：单元+集成全绿；关键流程覆盖率（语句）≥ 70%；集成测试只通过 API 与公开路径断言，不读内部实现细节。
